# Q&A crib: the four track-deck questions

Answer in one sentence, then show it on screen. Never claim something the screen cannot show. Items marked
**pending** need the Vultr VMs and credentials; check them off on the morning of the demo, or say plainly that
the answer comes from the local rehearsal.

## 1. "Show me the instance."

**Say:** "The engine and this app run on a Vultr VM. The agents' browsers run in gVisor sandbox pods on a
second VM, and the two VMs talk only over NetBird."

**Show:**
- The Vultr console with the two VMs. No credit codes or keys on screen.
- The run view `/run`, section **Sandbox proof**: the latest job's *Host check* (sandbox host, runtime `runsc`)
  and *Where it ran* (pod hostname and `uname` from inside the pod).
- `deploy/verify.sh remote <vm-ip> <urls>` output: the VM has no open app ports.

**Status:** the proof section and verify script are built and tested locally. Real host and runtime values
appear once the engine runs on the VMs **(pending)**.

## 2. "Is the model yours?" (or: whose model, where does inference run?)

**Say:** "Every agent call goes through Vultr Serverless Inference, behind one decision interface. Each artifact
records which backend and model produced it, and the app shows it."

**Show:**
- An approver review page: the header says "generated by `<model>` (`vultr`)".
- The absence of the "Simulated inference" banner. That banner appears on anything produced by recorded
  responses, and the definition-of-done check refuses to count such output.
- The model list from `https://api.vultrinference.com/v1/chat/models`, if asked which models exist.

**Status:** provenance (`generated_by`) and the banner are implemented. Until the key lands, every run is
`recorded` and shows the banner **(pending: first `vultr` run)**.

## 3. "Is Vultr planning and dispatching, or just hosting?"

**Say:** "The control plane on the Vultr VM plans the case and dispatches each step. The step stream shows the
decision for every step: plain download, script, agentic loop, or full computer use."

**Show:**
- `/run`: the phase timeline, then the step stream with its mode badges. Point at the single D0 download that
  covers the whole tax list, at a crystallized D1 macro, and at an S1 → S2 escalation.
- The "Where inference is spent" bars: inference is used only where the web is unpredictable.
- The case journal: any value traced back through the step, TDD, objective, ontology and PRD to the brief.

## 4. "If I paste `rm -rf /`, what dies?"

**Say:** "Only the sandbox pod for that job. It runs under gVisor with an egress allowlist, and it is deleted
when the job ends. The app never runs agent code, and its investigator container is read-only."

**Show:**
- `/run` → **Sandbox proof**: *Isolation probe* for every job, a non-allowlisted domain and a write outside the
  pod, both **BLOCKED**. Then *Teardown*: the pod is removed and no sandboxes are left.
- `deploy/verify.sh local`: the investigator container cannot write the case or its own root filesystem, and
  both app processes listen on loopback only.

**Status:** the engine's live Docker sandbox test shows network and write probes BLOCKED and teardown verified.
Running under `runsc` on the sandbox VM is **pending**.

## Likely follow-ups

- **"Where do the sources come from?"** The engine discovered them from the brief. The journal's case package
  table lists the objectives and technical definitions; none are hard-coded in either repo.
- **"Is this an accusation tool?"** No. Profiles are of legal entities, and flags are signals with a
  plain-language explanation, steps to verify, and a dispute path.
- **"What if the demo network fails?"** We replay a recorded real run from a local snapshot through the same run
  view (`pa-app snapshot` + `serve --replay`), and we say that it is a replay.
