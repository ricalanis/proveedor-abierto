# Q&A crib: the four judge questions (Blast Radius Zero)

The track deck spells out what the judge asks for each requirement (`docs/reference/event-decks.md` §1).
Answer in one sentence, then put the **exact screen** that proves it in front of the judge. Never claim more than
the screen shows. Items marked **pending** need the Vultr VMs; check them off before going on stage, or say
plainly that the answer comes from the local rehearsal.

Shared framing, in the deck's words:
- **"Two instances. One boundary."** VX1 #1 is the control plane (engine and this app). VX1 #2 is the sandbox
  host. They are joined by a private network, which for us is NetBird peer to peer.
- **"A container is not a sandbox."** On the isolation ladder (in-process → container → user-space kernel →
  microVM), we run **tier 03, gVisor `runsc`**, for every agent pod, and a throwaway Vultr instance (tier 04) is
  the escalation for anything riskier.
- **"Five checkpoints", each with verifiable output:** stdout / exit code / files / screenshot / hostname-uname.
  We show six: the deck's five plus secret hygiene.

## 1. "Show me the instance."

**Say:** "Two VX1 instances, one boundary. This control plane dispatches every agent task to the sandbox host
over a private NetBird network."

**Screen:** `/run` → **Sandbox proof** → latest job:
- *Host check*: sandbox host, runtime, and the `/dev/kvm` / CPU virtualization flags.
- *Where it ran*: pod hostname and `uname` from inside the pod.
- The **isolation tier** line above it reads "tier 3 · gVisor". If it says "tier 2 · container (runc)", we are on
  the laptop rehearsal and must say so.

Backup screens: the Vultr console showing both instances (no keys or credit codes on screen), and the NetBird
peers list (neutral peer names only).

**Status:** the screens are built. Real values come from VX1 #2 **(pending VM)**. The local mock run shows
runtime `runc` on OrbStack, and the tier line flags it honestly.

## 2. "Is the model yours, or a borrowed key?"

**Say:** "It's our own Vultr Serverless Inference subscription, behind one inference gateway on the control plane
that holds the only key. Every artifact records the backend and model that produced it, and every call is logged
against its session and step."

**Screen:**
- `/approvals/01-scope` (approver URL): the header reads "generated by `<model>` (vultr)".
- `/engine` → **Decisions by backend**: Vultr counts, plus Jev as a supporting backend. A Jev decision alone never
  makes a value gold, and the page flags any that does.
- No "Simulated inference" banner anywhere. That banner appears on anything from recorded responses, and those
  never count toward the definition of done.

**Status:** live inference works (CONTRACT v0.6). The first live run on the real case is next.

## 3. "Is Vultr planning and dispatching, or serving a static page?"

**Say:** "Vultr models plan each phase and decide each step. The control plane dispatches every step to a
sandbox pod and escalates only when the web is unpredictable."

**Screen:** `/run`:
- the phase timeline (Scope → Ontology → Fan out → Local scoping → Execute) with the approval checkpoints;
- the step stream with mode badges. Point at one D0 download, a macro crystallized to D1, and an S1 → S2
  escalation;
- **Where inference is spent**, the bars per mode.

Then `/journal/<value>`: the same value traced back through the step, the technical definition, the objective,
the ontology and the PRD to the brief.

## 4. "If I paste `rm -rf /`, what dies?"

**Say:** "Only that job's pod. It runs under gVisor behind an egress allowlist with memory, CPU, process and time
caps, it holds no secrets, and it is torn down when the job ends. Nothing runs inside this app."

**Screen:** `/run` → step stream, then **Sandbox proof**:
- A **limit kill** badge in the step stream when the extractor loops forever or runs `rm -rf /`: the job is
  stopped by its timeout or memory cap. The proof panel lists each job's limits (memory, CPU, processes, timeout,
  steps) and the jobs a limit killed.
- *Isolation probe*: a non-allowlisted domain, a write outside the pod, and a write outside the writable mount,
  all **BLOCKED**, for every job.
- *Secret hygiene*: no keys in the pod's environment or files (0 found); the cloud metadata IP and the NetBird
  mesh are **BLOCKED** from inside the pod. Every model call goes through the inference gateway on the control
  plane; a Skyvern brain in a cell holds only a session token with a dollar budget, revoked when the session closes.
  A hostile page's text is screened (Jev + Vultr content safety) and quarantined before any model reads it.
- *Teardown*: pod gone, proxy gone, network removed.
- *Task and real result*: the verifiable output (status or exit code, stdout when present, links to the captured
  file and screenshot).

Backup: `deploy/verify.sh local`. The app listens on loopback only, and the investigator container cannot write
the case or its own root filesystem.

**Status:** the proof panel renders the six checks and the limits. The engine emits limits, secret hygiene and
limit kills per CONTRACT §12 *(pending engine)*; the live Docker sandbox test already shows network and write
probes BLOCKED and teardown verified.

## Likely follow-ups

- **"Why gVisor and not a platform like OpenSandbox or E2B?"** "We think in Docker. gVisor is the wall; we wrote
  the orchestration and the egress proxy ourselves, and the proof checkpoints show that they hold."
- **"How do people reach the app?"** "Only through NetBird: two URLs, one per role, each with its own credential,
  and zero inbound ports on the VMs, SSH included." (`deploy/verify.sh remote`)
- **"Where do the sources come from?"** "The engine discovered them from the one-sentence brief. The journal
  lists them; none are hard-coded."
- **"Is this an accusation tool?"** "No. We profile legal entities. Every flag comes with the rule, the
  evidence, the steps to verify it, and a dispute path."
- **"What if the network fails on stage?"** "We replay a recorded real run from a local snapshot through the
  same view, and we say that it's a replay."
